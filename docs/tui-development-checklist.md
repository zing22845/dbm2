# TUI 程序开发指引 Checklist

> 适用对象：基于事件驱动的终端 UI 程序（编辑器、仪表盘、文件管理器等）。
> 覆盖：Rust (ratatui/crossterm)、Go (bubbletea)、Python (Textual)、Node (blessed) 等主流框架。

---

## 0. 核心结论

- [ ] 采用 **事件驱动 (event loop)** 作为程序主干。
- [ ] 在事件驱动之上使用 **单向数据流**：`事件 → 更新模型 → 渲染视图`（Elm 架构 / TEA，如 bubbletea）。
- [ ] 复杂交互用显式 **状态机** 管理（如 vim 的多模式），不要用散落的布尔标志。
- [ ] 澄清误区：终端 UI 通常是 **即时模式 (immediate mode) 渲染 + 离屏缓冲 + 差异渲染**，而非 GUI 的"保留模式"。

---

## 1. 架构与数据流

- [ ] 主循环：读取事件 → 分发 → 更新模型 → 重绘 → 直到退出。
- [ ] 将应用建模为 **Model / Update / View**，保持数据单向流动。
- [ ] 用状态机表达模式（normal / insert / visual 等）；同一按键在不同模式下行为不同。
- [ ] 把事件分发给对应处理器，处理器只改模型、不直接绘制。
- [ ] 避免"事件处理函数里直接写数据库 / 网络 / 重计算"——通过消息通道把副作用交给后台任务，再以事件回传结果。

---

## 2. 渲染模型（修正点）

- [ ] 使用 **即时模式**：每个 frame 重建整帧 UI（ratatui 风格）。
- [ ] 依赖框架的 **离屏缓冲 (back buffer)** 与 **差异渲染 (diff)**，只输出变化的单元格，减少闪烁与流量。
- [ ] 不要在事件处理里"逐格擦除再画"；交给框架统一刷屏。
- [ ] 复用 Buffer / 减少每帧堆分配，性能敏感路径注意避免分配热点。
- [ ] 布局计算与"生成视图"分离，便于单测与 snapshot 比对。

---

## 3. 终端健壮处理（修正点）

- [ ] 进入 **非规范/原始模式 (raw mode)**，按按键而非行缓冲读取；最后**必须恢复**。
- [ ] 用 `defer` / `Drop` / `panic hook` 兜底，确保崩溃或 Ctrl+C 也能恢复终端。
- [ ] 进入并正确退出 **Alternate Screen Buffer**，避免退出后界面残留在滚动区。
- [ ] 监听 **窗口尺寸变化**：Unix 用 `SIGWINCH`，但应依赖框架抽象出的 resize 事件（Windows 由库内部处理，不要假设信号语义）。
- [ ] 处理 `SIGINT` / `SIGTERM` 实现**优雅退出**。
- [ ] 键盘/鼠标的多字节 **CSI 转义序列**交给成熟跨平台库（crossterm / termion / ncurses），不要自己解析。
- [ ] **宽字符 / CJK 处理**：布局与光标定位按显示宽度（中文=2）计算，否则会错位。
- [ ] 鼠标支持使用 SGR 编码，由库处理。

---

## 4. 组件化 / 分层

- [ ] 界面拆分为独立、可组合的 **组件 (Widget)**：按钮、列表、输入框、面板，各自管理状态与绘制区域。
- [ ] 容器组件负责布局，并向子组件**委托**绘制与事件。
- [ ] 组件间通过 props / 消息通信，避免共享可变全局状态。
- [ ] 散落的绘制逻辑收敛到组件里，提升可维护性与可测试性。

---

## 5. 关注点分离（UI 与业务逻辑解耦）

- [ ] 核心领域逻辑抽到独立模块 / 服务，UI 层只负责展示与派发动作。
- [ ] 采用 MVP / MVVM，或消息通道把 I/O 副作用交给后台任务。
- [ ] 后台任务完成后，以事件形式回传结果给主循环再更新 UI。

---

## 6. 异步与并发

- [ ] 事件循环必须保持响应：**耗时操作**（文件、网络、计算）异步化或放到线程。
- [ ] 完成后再向 UI 发送事件，切勿在事件处理里阻塞主循环。
- [ ] 界面更新必须回到主事件循环（或通过线程安全的消息队列同步）。
- [ ] 日志 I/O 等也不要在主循环里同步阻塞。

---

## 7. 终端能力检测与渐进增强

- [ ] 查询 `TERM` / `COLORTERM`（如 `truecolor`）决定真彩色 / 256 色 / 基础色。
- [ ] 遵循 **`NO_COLOR`** 标准，提供可关闭彩色的模式。
- [ ] 鼠标、真彩色等能力按检测结果**渐进增强**，缺失时优雅降级。
- [ ] 不假设终端宽度，支持 Resize，设置**最小尺寸约束**。
- [ ] 提供可访问性 / 高对比度主题。

---

## 8. 可测试性

- [ ] 渲染逻辑与"视图生成"分离：生成可比对字符串 / 格子矩阵，不直接写屏。
- [ ] 借助 `ratatui` 的 `TestBackend` 或 Textual 的 pytest 集成做 **snapshot 测试**。
- [ ] 事件分发、状态转换、布局计算可单独单元测试。
- [ ] 使用模拟终端或记录-回放工具做集成测试。

---

## 9. 调试与日志

- [ ] TUI 霸屏无法用 `printf` 调试，**日志务必写入文件**。
- [ ] 开发期开启日志，记录事件与状态变更，提高排错效率。
- [ ] 使用结构化日志（如 `env_logger` / `RUST_LOG`），并注意不要阻塞事件循环。

---

## 10. 用户体验与无障碍

- [ ] 支持常见键盘操作：Tab 导航、方向键、可配置快捷键。
- [ ] 列表 / 表格提供搜索、滚动、行号。
- [ ] 控制文本输出顺序，兼顾屏幕阅读器的基本兼容。
- [ ] 遵循平台习惯的键位约定，提供键位自定义能力。

---

## 附：常见误区澄清

| 误区 | 修正 |
| --- | --- |
| TUI 用"保留模式"渲染 | 实际多为**即时模式 + 离屏缓冲 + 差异渲染** |
| 只要恢复原始模式即可 | 还需正确进入/退出 **Alternate Screen Buffer** |
| `SIGWINCH` 是通用机制 | 它是 Unix 信号；Windows resize 由框架抽象，应用应依赖框架事件 |
| 中文终端无需特殊处理 | 双宽字符需在布局/光标按宽度 2 计算 |
| 事件驱动"唯一合理" | 基于行编辑的简单交互式 CLI（readline/prompt）仍可用阻塞式输入 |
